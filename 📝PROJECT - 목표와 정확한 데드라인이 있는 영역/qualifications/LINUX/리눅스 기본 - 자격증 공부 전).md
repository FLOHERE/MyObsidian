> 이 강의는 Linux 커널 자체가 아니라, **Linux와 macOS 같은 유닉스 계열 시스템에서 셸과 터미널을 쓰는 법**을 전제로 해요. 먼저 입력과 명령 실행의 역할을 구분하고, 그다음 파일 위치를 읽는 법을 익히면 돼요. 이후에는 명령 사이에 데이터를 연결하고, 종료 코드로 결과를 확인하는 흐름으로 이어져요.
>
> ![](https://resource.lilys.ai/images/genimg_1d533b9efe2d4f2f.png)
>
> - **터미널은 글자를 주고받는 창이고, 셸은 명령을 실행하는 프로그램이에요.**
>   - 예를 들어 터미널에 `echo "hello world"`를 입력하고 Enter를 누르면, 터미널은 입력한 글자를 셸에 전달하고 실행 결과를 화면에 보여 줘요.
>   - 셸은 명령을 **읽고(Read), 해석·실행하고(Evaluate), 결과를 내보낸(Print), 다시 입력을 기다려요(Loop)**. 이 반복을 REPL이라고 불러요.
>   - 그래서 터미널 창을 바꿔도 셸의 역할은 같을 수 있어요. 터미널 에뮬레이터는 화면과 키보드 쪽, 셸은 명령 해석 쪽을 맡아요.
>
> - **`/`에서 시작하는 경로는 절대 경로, 현재 위치에서 출발하는 경로는 상대 경로예요.**
>   - 파일 시스템은 폴더와 파일이 층층이 들어 있는 나무 같은 구조예요. 맨 위의 기준점인 루트 디렉터리를 `/`로 써요.
>   - 강의 예시에서 현재 위치가 `/users/Wags Lane`이라면, `/users/Wags Lane/World Bank`는 루트부터 위치를 모두 적은 **절대 경로**예요. `/`로 시작하므로 현재 위치가 달라져도 같은 곳을 가리켜요.
>   - 같은 현재 위치에서 `World Bank`라고 쓰면 **상대 경로**예요. 지금 있는 `/users/Wags Lane` 안에서 `World Bank`를 찾는다는 뜻이라, 다른 곳으로 이동하면 같은 이름도 다른 위치를 가리키거나 찾지 못할 수 있어요.
>
> - **표준 입력·출력·에러는 프로그램이 데이터를 주고받는 기본 통로예요.**
>   - `stdin`(표준 입력)은 프로그램이 읽는 통로, `stdout`(표준 출력)은 정상 결과를 내보내는 통로, `stderr`(표준 에러)는 오류나 진단 메시지를 내보내는 통로예요.
>   - `echo "hello" > hello.txt`처럼 `>`를 쓰면 정상 출력이 화면 대신 파일로 가요. `2>`는 오류 통로를 따로 돌려요. 예를 들어 `ls missing 2> errors.txt`는 오류 메시지를 `errors.txt`에 보내요.
>   - `|`는 한 명령의 표준 출력을 다음 명령의 표준 입력으로 연결해요. `cat transactions.csv | grep suspicious`라면 파일 내용이 `grep`으로 흘러가고, `grep`은 그중 `suspicious`가 들어간 줄을 골라요. 출력을 파일에 저장하는 `>`와 달리, 파이프는 명령끼리 데이터를 이어 줘요.
>
> - **종료 코드는 명령의 결과를 숫자로 알려 줘요.**
>   - 명령이 끝나면 셸은 성공 여부를 나타내는 숫자를 남겨요. 관례상 `0`은 성공이고, `0`이 아닌 값은 실패나 다른 문제를 뜻해요.
>   - `ls`를 실행한 직후 `echo $?`를 입력하면 가장 최근 명령의 종료 코드를 확인할 수 있어요. `$?`는 그 값을 담아 둔 셸 변수라서, 다른 명령을 실행하면 값이 바뀔 수 있어요.
>   - 이 숫자는 다음 동작을 정할 때도 쓰여요. 예를 들어 `command && echo "성공"`은 앞 명령의 종료 코드가 `0`일 때만 뒤의 `echo`를 실행해요.

## 2. 터미널과 셸의 기초 

이 장에서는 텍스트로 컴퓨터와 상호작용하는 CLI를 소개하고, 터미널과 셸이 서로 다른 역할을 한다는 점을 설명한다.

### 2.1 CLI와 GUI의 차이 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/254.jpg)

1. **CLI는 텍스트 명령으로 컴퓨터와 상호작용하는 방식이며, GUI와는 입력 방식과 활용 특성이 다르다.** 
   2. 강의 화면에는 오른쪽의 터미널 에뮬레이터 Ghostty와 왼쪽의 강의 지시문이 나란히 나타난다. 
   3. Mac에서는 Ghostty나 기본 터미널을 사용할 수 있고, Windows에서는 명령 프롬프트를 열 수 있지만 이후 과정에는 WSL이 필요하다. 리눅스 사용자는 자신의 터미널을 열면 된다. 
   4. 터미널에 `echo "hello world"`를 입력하면 콘솔에 `hello world`가 출력된다. 이는 Python의 `print("hello world")`나 Go의 `fmt.Println("hello world")`와 비슷한 역할을 한다. 
   5. 프로그래머들은 터미널, 셸, 명령줄, CLI, 명령 프롬프트라는 말을 느슨하게 섞어 쓰곤 한다. 정확한 뜻은 조금씩 다르지만, 대체로 텍스트를 통해 컴퓨터와 상호작용하게 해주는 프로그램이나 환경을 가리킨다. 
   6. GUI(그래픽 사용자 인터페이스)는 Windows 바탕 화면처럼 메뉴, 아이콘, 창을 보고 마우스로 조작하는 시각적 방식이다. 
   7. CLI(명령줄 인터페이스)는 복잡한 버튼과 메뉴 대신 텍스트만으로 상호작용하는 방식이다. 프로그램을 실행할 때 아이콘을 누르는 대신 이름을 입력하고, 파일을 볼 때 문서 편집기를 여는 대신 명령을 입력한다. 
   8. GUI는 처음 사용하기 쉽고 스스로 설명하는 요소가 많지만, 제공된 버튼과 위젯의 범위를 벗어나기 어렵다. 반면 CLI는 시스템의 더 낮은 수준에 직접 접근할 수 있어 더 강력하다. 
   9. 강의자는 개발자라면 명령줄 사용에 익숙해지는 일이 선택 사항이 아니라고 강조한다. 

10. **실무에서는 GUI를 쓰는 개발자도 있지만, 명령줄은 자주 쓰이는 실행 방식이다.** 
   11. 입문 과정에서는 브라우저에서 코드를 작성하고 실행 버튼을 누르기도 하지만, 실제 개발에서는 프로그램을 명령줄에서 실행하는 경우가 흔하다. 이는 특히 강의자의 웹 개발 경험을 반영한 설명이며, 모든 개발 환경에 해당하는 것은 아니다. 
   12. IDE에서 실행 버튼을 사용하는 개발자도 전문성이 떨어지는 것은 아니다. 다만 명령줄을 익혀두면 실제 업무에서 유용하게 쓰인다. 
   13. 강의자는 Python 코드를 실행할 때 편집기의 실행 버튼보다 터미널에서 `python main.py`를 입력하는 방식을 주로 쓴다. 이는 그가 개발 환경을 구성하는 개인적인 방식이다. 
   14. CLI는 애플리케이션과 프로그램을 텍스트로 조작하는 인터페이스다. GUI를 이용하는 사람은 아이콘을 클릭하고, Windows Explorer나 Mac Finder에서 폴더를 찾아가며, 마우스를 사용한다. 
   15. CLI는 명령어를 익혀야 해서 처음에는 더 어렵지만, 익숙해지면 입력 속도만큼 빠르게 작업할 수 있고 자동화하기도 쉽다. 마우스 클릭을 흉내 내는 프로그램보다 텍스트를 처리하는 프로그램을 만들기 쉽기 때문이다. 
   16. `who am I` 명령을 실행하면 현재 로그인한 사용자 이름이 출력된다. 강의자의 Mac에서는 `Wags Lane`이 출력되었으며, 과제에서는 자신의 사용자 이름이 콘솔에 출력된 것이 무엇을 뜻하는지 답한다. 

### 2.2 Windows에서 WSL을 준비하고 운영체제 차이를 이해하기 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/534.jpg)

1. **Windows 사용자는 기본 명령 프롬프트 대신 WSL의 리눅스 환경을 사용한다.** 
   2. 강의자는 Mac을 사용하므로 WSL 설치 시연은 건너뛰고, Windows 사용자는 과정 1장 3번째 수업의 안내를 따라 설치하라고 한다. 
   3. 강의자는 수천 명의 학생이 WSL을 설치해 사용했다고 말하며, Windows를 망가뜨리거나 디스크를 나누는 이중 부팅을 해야 하는 방식이 아니라 비교적 간단한 설정이라고 설명한다. 
   4. 설정을 마치면 Windows 안에서 Bash 셸을 사용하는 리눅스 터미널을 쓸 수 있고, 나머지 과정을 따라갈 수 있다. 
   5. 과정의 명령은 Linux의 Bash와 Mac의 Zsh에서 작동하며, 두 운영체제가 Unix 계열이므로 다루는 내용이 충분히 비슷하다. 

### 2.3 터미널과 셸, REPL의 역할 

강의자는 일상 대화에서는 터미널과 셸을 같은 뜻처럼 말하기도 하지만, 엄밀히 보면 두 프로그램의 역할은 다르다고 설명한다.

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/666.jpg)

1. **터미널 에뮬레이터는 텍스트를 입력받고 화면에 출력하는 창이며, 셸은 명령을 해석하고 실행한다.** 
   2. 프로그래머들은 터미널, 셸, CLI를 비슷한 뜻으로 부르는 경우가 많지만, 각각의 엄밀한 정의는 다르다. 
   3. 과거의 터미널은 모니터와 키보드를 결합한 물리 장치였다. 당시 사용자는 그 장치를 통해 소프트웨어와 상호작용했다. 
   4. 오늘날에는 Ghostty 같은 **터미널 에뮬레이터**를 많이 사용한다. 이는 물리 터미널의 동작을 흉내 내며, 텍스트를 입력받고 결과를 화면에 표시하는 프로그램이다. 
   5. 터미널 자체는 명령을 해석하지 않아도 된다. 터미널이 입력과 표시를 맡는다면, **셸은 터미널에 입력된 명령을 실제로 처리하는 프로그램**이다. 
   6. 셸은 입력을 읽고, 명령의 뜻을 평가하고, 실행한 결과를 출력한 다음, 다음 입력을 받을 준비를 한다. 이 반복 구조를 REPL(Read-Evaluate-Print Loop, 읽기-평가-출력 반복)이라고 한다. 

7. **Bash와 Zsh에서는 명령 실행뿐 아니라 계산과 변수 사용도 할 수 있다.** 
   8. 강의자는 셸에 숫자 덧셈 식을 입력해 결과를 출력하고, 그 결과를 과제란에 붙여넣는 시범을 보인다. 셸이 단순히 문자열을 출력하는 것 외에도 입력을 평가할 수 있음을 보여주는 예다. 
   9. Bash와 Zsh는 REPL이면서 간단한 스크립트를 작성할 수 있는 프로그래밍 언어이기도 하다. 더 복잡한 작업도 할 수 있지만, 보통 큰 웹 애플리케이션을 만드는 데 가장 적합한 언어는 아니다. 
   10. 셸에서는 변수를 만들고 사용할 수 있다. 예를 들어 `name=Lane`처럼 변수를 설정하며, 변수를 사용할 때는 `$name`처럼 이름 앞에 달러 기호를 붙인다. 설정할 때는 달러 기호를 붙이지 않는다. 
   11. `echo`로 변수를 출력하면 셸이 변수 값을 문자열 안에 넣어 출력한다. 

### 2.4 과정의 이야기 설정과 셸 변수 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/948.jpg)

1. **실습은 World Bank의 보안 침해를 조사하는 가상의 포렌식 개발자 역할로 진행된다.** 
   2. 수강자는 가상의 World Bank에 고용되어 보안 침해를 조사하는 포렌식 개발자 역할을 맡는다. 강의자는 조직이 일을 잘 모르는 대기업이라는 설정을 농담처럼 덧붙인다. 
   3. 수강자는 아직 전문가가 아니지만, 다른 사람의 비용으로 배우는 상황이라는 이야기 속에서 파일 탐색, 텍스트 조작, 프로그램 실행을 연습한다. 
   4. 파일을 살펴보고, `grep`으로 텍스트를 찾고, `find`로 파일을 찾고, 결과를 출력하면서 Unix 계열 시스템을 실제로 탐색한다. 
   5. Mac의 명령줄 작업은 Linux와 비슷하지만, 서버 관리와 로컬 개발이 완전히 동일한 것은 아니다. Windows는 이 환경과 다르므로 WSL을 사용한다. 

6. **셸 변수로 조사 상황에 맞는 문장을 출력하고, `history`와 방향키로 이전 명령을 다룬다.** 
   7. 첫 실습에서는 `Bank name`에 `World Bank`, `founded`에 `1969`, `CEO`에 `Jeff Gates`를 변수로 설정한다. 
   8. 이어서 `echo`와 변수 값을 사용해 “World Bank was founded in 1969 by Jeff Gates”라는 문장을 출력한다. 강의 시연에서는 `founded`를 `found`라고 말하는 부분이 있지만, 출력 문장은 “was found in”으로 나타난다. 
   9. 셸은 입력한 명령을 기록하며, `history` 명령으로 최근 실행한 명령 목록을 확인할 수 있다. 강의자의 화면에는 최근 약 15개 명령이 나타난다. 
   10. 다음 실습에서는 `department=Engineering`, `team=Ops`를 설정하고, `echo`로 “I work in Engineering on Ops”라는 취지의 문장을 출력한 뒤 `history` 결과를 제출한다. 

### 2.5 화면 지우기, 명령 이력, 터미널 에뮬레이터 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/1162.jpg)

1. **`clear`는 화면만 지우며, 위쪽 화살표와 아래쪽 화살표는 명령 이력을 오간다.** 
   2. 터미널 화면이 복잡해지면 `clear`를 입력해 화면을 정리할 수 있다. 이 명령은 화면을 지우지만 `history`에 남은 기록은 삭제하지 않는다. 
   3. 명령을 다시 입력하고 싶지 않을 때 위쪽 화살표를 누르면 이전 명령이 나타난다. 위쪽 화살표를 반복해서 누르면 더 과거의 명령으로 이동한다. 
   4. 아래쪽 화살표는 반대 방향으로 이동해 더 최근 명령을 보여주며, 마지막에는 빈 입력 상태로 돌아온다. 예를 들어 `echo one`, `echo two`, `echo three`를 입력한 뒤 위쪽 화살표로 거슬러 올라가고, 아래쪽 화살표로 다시 내려올 수 있다. 
   5. 과제의 정답은 위쪽 화살표가 과거로 이동하고 아래쪽 화살표가 미래, 즉 더 최근 명령으로 이동한다는 것이다. `clear`는 새 터미널 창을 만들거나 기록을 삭제하는 것이 아니라 화면을 지운다. 

6. **터미널 에뮬레이터는 여러 선택지가 있으며, 과정에서는 원하는 것을 사용하면 된다.** 
   7. 강의자는 Mitchell Hashimoto가 만든 새 터미널 에뮬레이터 Ghostty를 사용한다. 그는 HashiCorp의 창립자이며, 강의자는 Ghostty를 좋게 평가한다. 
   8. 다른 선택지로 Alacritty가 있으며, 강의자는 당시 가장 흔한 터미널 에뮬레이터라고 생각한다고 말한다. 
   9. 강의자가 주로 쓰는 편집기 Zed는 Alacritty를 내부적으로 사용하는 것 같다고 추측한다. 그는 대부분 편집기에 내장된 터미널을 사용한다. 
   10. VS Code와 Cursor에도 내장 터미널이 있고, Vim이나 Neovim처럼 터미널에서 실행되는 편집기를 사용할 때는 Ghostty 같은 독립형 터미널 에뮬레이터를 쓰는 경우가 많다. 
   11. 과정에서는 기본 터미널을 포함해 원하는 에뮬레이터를 선택하면 된다. 퀴즈에서 제시된 선택지 중 Ubuntu는 터미널 에뮬레이터가 아니라 운영체제다. 

## 3. 파일 시스템과 경로 탐색 

이 장에서는 디렉터리와 파일을 트리 구조로 이해하고, 경로와 기본 파일 명령을 이용해 World Bank 자료를 탐색한다.

### 3.1 파일 시스템, 현재 위치, 절대 경로 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/1319.jpg)

1. **파일 시스템은 루트 디렉터리에서 시작해 디렉터리와 파일이 이어지는 트리 구조다.** 
   2. 대부분의 컴퓨터 사용자는 폴더가 서로 안에 들어가는 구조에 익숙하다. Unix 계열 시스템에서는 폴더를 디렉터리라고 부르며, 파일 시스템은 이런 디렉터리가 계층을 이루는 구조다. 
   3. 구조가 아주 깊어질 수는 있지만 컴퓨터 저장 공간이 무한한 것은 아니다. 디렉터리는 다른 디렉터리와 파일을 담는다. 
   4. 파일은 근본적으로 이진 데이터 덩어리와 그 파일을 설명하는 메타데이터로 볼 수 있다. 이미지, 텍스트, PDF, 코드 등 어떤 데이터든 저장할 수 있으며, 파일을 읽는 프로그램이 그 데이터를 해석하고 목적에 맞게 사용한다. 

5. **현재 작업 디렉터리와 `pwd`를 이용하면 파일 시스템에서 자신의 위치를 확인할 수 있다.** 
   6. 터미널을 열면 사용자는 특정 디렉터리에서 시작하며, 보통 홈 디렉터리다. 
   7. `pwd`는 `print working directory`의 약자로, 현재 작업 디렉터리의 경로를 출력한다. 강의자의 Mac에서는 `/Users/SL Wags Lane`처럼 나타난다. 
   8. `/`는 파일 시스템의 루트 디렉터리이며, 그 아래에 `Users`가 있고, 그 안에 사용자 이름에 해당하는 디렉터리가 있다. 
   9. World Bank 직원의 의심스러운 컴퓨터에 원격으로 접속했다는 실습에서는 `pwd`를 실행해 현재 위치를 확인하고 전체 출력 결과를 제출한다. 

10. **파일 경로는 파일 시스템에서 파일이나 디렉터리의 위치를 나타내는 텍스트다.** 
   11. Windows Explorer나 Mac Finder는 디렉터리 트리를 시각적으로 보여준다. 파일 경로는 그 위치를 텍스트로 나타낸 것이다. 
   12. **절대 경로(absolute path)**는 루트 디렉터리에서 시작하며, 각 디렉터리 이름은 `/`로 구분한다. 
   13. 경로의 마지막 부분은 파일을 가리키면 파일 이름이고, 디렉터리를 가리키면 디렉터리 이름이다. 예를 들어 `/documents/school/homework.txt`는 파일을, `/documents/school`은 디렉터리를 가리킨다. 
   14. `pwd`의 출력은 현재 위치를 나타내는 파일 경로다. 경로는 긴 경우 직접 입력하기 번거롭지만, 프로그램에서 특정 파일을 가리킬 때는 편리하고 오류가 적다. 
   15. `/users/lane`에서 첫 번째 `/`는 루트를 뜻하고, 그 아래 `users`, 그 아래 `lane`이 이어진다. 따라서 이 경로는 루트에서 두 단계 내려간 위치다. 
   16. 조사 실습에 필요한 World Bank 폴더는 Boot.dev GitHub에서 내려받아 현재 디렉터리에 풀어둔다. Windows 사용자는 이 단계에서 Ubuntu WSL 터미널을 사용해야 한다. 

### 3.2 `ls`, `cd`, 자동 완성과 부모 디렉터리 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/1578.jpg)

1. **`ls`로 내용을 확인하고 `cd`로 위치를 바꾸며, Tab 키로 디렉터리 이름을 자동 완성할 수 있다.** 
   2. World Bank 폴더를 현재 디렉터리로 내려받아 압축을 풀면 홈 디렉터리 안에 `World Bank` 디렉터리가 생긴다. `ls`는 현재 디렉터리의 내용을 보여준다. 
   3. `cd`는 디렉터리를 바꾸는 명령이다. `cd World Bank`를 입력해 World Bank 디렉터리로 이동한다. 
   4. 디렉터리 이름의 일부를 입력한 뒤 Tab을 누르면 현재 위치에 있는 이름을 자동 완성할 수 있다. 예를 들어 `WORL` 뒤에 Tab을 누르면 `World Bank`가 채워진다. 이름을 끝까지 직접 입력해도 된다. 
   5. 이동한 뒤에는 셸 프롬프트가 현재 위치를 다르게 표시할 수 있다. `ls`를 실행하면 World Bank 디렉터리 안의 네 항목을 볼 수 있으며, 과제에서는 그 결과를 제출한다. 
   6. 시연 중 결과에 `go.mod`가 포함되는 부분은 강의자가 잘못 들어간 파일일 수 있다고 말한다. 이후 수강할 때 해당 항목이 없어도 정상이며, 삭제했기 때문이라고 안내한다. 

7. **`cd ..`는 부모 디렉터리로 올라가며, `ls`에는 다른 디렉터리를 지정해 내용을 확인할 수도 있다.** 
   8. `cd ..`는 현재 위치에서 한 단계 위인 부모 디렉터리로 이동한다. World Bank에서 실행하면 홈 디렉터리로 돌아간다. 
   9. 홈 디렉터리에서 `ls`만 입력하면 홈의 내용을 본다. 반면 `ls World Bank`처럼 디렉터리를 인수로 지정하면 그 디렉터리 안으로 이동하지 않고도 내용을 확인할 수 있다. 

### 3.3 절대 경로와 상대 경로 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/1770.jpg)

1. **절대 경로는 현재 위치와 무관하지만, 상대 경로는 현재 작업 디렉터리에 따라 의미가 달라진다.** 
   2. 상대 경로(relative path)는 현재 위치를 기준으로 파일이나 디렉터리를 가리킨다. 현재 위치가 `/users/Wags Lane/World Bank`라면 그 위치를 기준으로 한 `World Bank` 같은 이름이 상대 경로가 된다. 
   3. 절대 경로는 루트에서 시작하는 전체 경로다. 어디에 있든 같은 위치를 가리키며, 강의에서는 `/users/Wags Lane`을 예로 든다. 
   4. 강의자는 절대 경로를 집 주소에, 상대 경로를 “두 블록 가서 모퉁이를 돌아라” 같은 길 안내에 비유한다. 집 주소는 어디서든 목적지를 찾을 수 있지만, 상대적인 길 안내는 현재 서 있는 곳에 따라 달라진다. 
   5. 절대 경로는 `/`로 시작하고, 상대 경로는 `/`로 시작하지 않는다는 점이 구분 기준이다. 
   6. `/users/Wags Lane/World Bank`로 이동하는 것은 절대 경로를 쓰는 예다. 이미 World Bank 안에 있는데 `cd World Bank`를 입력하면 그 안에 다시 `World Bank`가 없으므로 실패한다. 한 단계 올라간 뒤에는 상대 경로로 다시 들어갈 수 있다. 

7. **일반적인 작업에는 상대 경로가 편하고, 시스템 전체 위치를 정확히 지정할 때는 절대 경로가 유용하다.** 
   8. 터미널에서 현재 작업 디렉터리 주변을 탐색할 때는 상대 경로를 자주 쓴다. 예를 들어 파일을 나열하거나 하위 디렉터리로 이동할 때 상대 경로가 편리하다. 
   9. 프로그램 설치 위치처럼 시스템 전체에서 정확히 알아야 하는 위치를 다룰 때는 절대 경로가 유용하다. 그래야 프로그램을 실행하거나 제거할 때 위치를 찾을 수 있다. 
   10. 퀴즈에서는 `/`로 시작하지 않는 경로가 상대 경로이고, 현재 작업 디렉터리에 상관없이 같은 파일을 가리키는 경로가 절대 경로라고 확인한다. 

### 3.4 파일 내용 읽기: `cat`, `head`, `tail`, `less` 

어떤 명령을 쓸지는 파일 크기와 필요한 내용에 따라 달라진다. 파일 전체를 출력하는 `cat`, 일부 줄을 출력하는 `head`와 `tail`, 페이지 단위로 살피는 `less`가 소개된다.

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/2179.jpg)

1. **`cat`은 파일 내용을 출력하며, 이름은 여러 파일을 이어 붙이는 기능에서 왔다.** 
   2. 파일은 파일 시스템이 위치를 추적하는 데이터 덩어리이며, 경로를 이용해 파일을 찾는다. 파일 형식이나 메타데이터가 있어도 그 밑바탕은 데이터 자체다. 
   3. `cat`은 파일 내용을 출력한다. 이름은 concatenate(이어 붙이다)에서 왔는데, 여러 파일의 내용을 연결해 출력할 수 있기 때문이다. 
   4. 실제로는 파일 하나를 출력할 때 자주 쓰이므로, 이름만 보면 용도가 헷갈릴 수 있다. 핵심은 `cat`으로 하나 이상의 파일 내용을 출력할 수 있다는 점이다. 
   5. 실습에서는 World Bank의 `public` 디렉터리로 이동해 `PR ideas.txt`를 찾고, `cat`으로 파일 내용을 출력해 제출한다. 강의자의 말에서는 파일 이름을 `PR.txt`라고 부르는 부분이 있지만, 화면에서 확인하는 이름은 `PR ideas.txt`다. 

6. **파일이 큰 경우 `head`와 `tail`로 앞이나 뒤의 일부만 확인한다.** 
   7. 서버 로그는 매우 커질 수 있어 `cat`으로 전부 출력하면 터미널이 많은 텍스트를 처리하느라 오래 걸릴 수 있다. 이런 경우 `head`와 `tail`을 쓰면 필요한 부분만 볼 수 있다. 
   8. `head`는 파일의 처음부터 지정한 개수만큼 줄을 출력하고, 줄 수를 지정하지 않으면 기본값은 10줄이다. `tail`은 끝에서부터 지정한 줄 수를 출력한다. 
   9. 거래 자료 실습에서는 `private/transactions`로 이동해 `2023.CSV`를 `cat`으로 살펴본다. 파일이 길기 때문에 전체를 읽기 어렵다. 
   10. `head -n 6 2023.CSV`는 첫 6줄을 출력한다. CSV의 첫 줄은 열 이름을 담은 헤더이며, CSV는 스프레드시트와 비슷한 내용을 텍스트로 표현한 형식이다. 
   11. `tail -n 5 2023.CSV`는 마지막 5줄을 출력한다. 과제에서는 첫 6줄과 마지막 5줄, 총 11줄을 합쳐 제출한다. 

12. **`less`는 파일을 대화형 화면에서 살펴보는 도구이며, `more`보다 기능이 많다.** 
   13. `more`와 `less`는 파일 내용을 한 화면이나 한 줄씩 살펴보게 해준다. 강의자는 `less`가 `more`보다 발전된 도구이므로, `less`가 없다면 `more`를 쓰는 정도로 설명한다. 
   14. 2023년 거래 파일의 앞과 뒤에서 수상한 내용을 찾지 못했으므로, 이제 `less 2023.CSV`로 파일 중간도 살펴본다. 
   15. `less`를 실행하면 셸 프롬프트 대신 파일을 보는 대화형 화면이 열린다. Enter로 아래로 이동하고, 다른 터미널 기반 프로그램처럼 실행 중에는 프롬프트를 사용할 수 없다. 
   16. `q`를 누르면 `less`에서 나올 수 있다. 강의자는 많은 터미널 프로그램에서 `q`가 종료 키로 쓰이지만 Vim은 예외라서 빠져나오는 법이 어렵게 느껴질 수 있다고 덧붙인다. 
   17. `less -N 2023.CSV`는 줄 번호를 표시한다. 스페이스바로 한 페이지 아래로 이동하고 `b`로 한 페이지 위로 이동할 수 있다. 
   18. 실습에서는 153번째 줄을 찾아 내용을 제출한다. 강의자는 줄이 화면 끝에 걸려 위치를 조정하려다 어려움을 겪지만, 해당 줄을 확인해 과제에 붙여 넣는다. 

### 3.5 파일과 디렉터리 만들기·이동·삭제·복사 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/2494.jpg)

1. **`touch`는 파일의 시간 정보를 갱신하며, 파일이 없으면 빈 파일을 만든다.** 
   2. `touch`는 파일의 접근 및 수정 시각을 갱신한다. 지정한 파일이 없으면 그 이름으로 빈 파일을 만든다. 
   3. 강의자는 자동화 작업에서 시간 정보 갱신이 필요한 경우도 있지만, 자신은 `touch`를 주로 새 파일을 빠르게 만들 때 사용한다고 설명한다. 
   4. 신용카드 기록이 있어야 하는데 해당 파일이 없다는 설정에서 `World Bank/public/products/credit cards`로 이동해 `touch credit history.txt`를 실행한다. 
   5. `ls`로 파일이 만들어졌는지 확인하고 신용카드 디렉터리의 내용을 제출한다. 

6. **`mkdir`는 현재 디렉터리 안에 새 디렉터리를 만든다.** 
   7. 디렉터리는 파일이나 다른 디렉터리를 담는 위치다. Windows에서는 흔히 폴더라고 부르지만 같은 개념이다. 
   8. `mkdir`는 `make directory`의 줄임말이며, 현재 위치에 새 디렉터리를 만든다. 
   9. 실습에서 `credit cards` 안의 파일 하나가 잘못 놓여 있는 것으로 보인다. `pwd`로 현재 위치가 `World Bank/public/products/credit cards`인지 확인하고, `cd ..`로 `products` 디렉터리로 올라간다. 
   10. `mkdir Investments`로 투자 디렉터리를 만든 뒤 `ls`로 확인하고, `products` 디렉터리의 내용을 제출한다. 

11. **`mv`는 파일 경로를 바꾸며, 파일 이동과 이름 변경을 모두 수행할 수 있다.** 
   12. `mv`는 파일이나 디렉터리를 다른 위치로 옮기며, 파일 이름을 바꾸는 데도 쓸 수 있다. 
   13. 명령줄에서는 이동과 이름 변경이 모두 파일 경로를 바꾸는 일이다. GUI에서는 다른 동작처럼 보이지만, 결국 파일이 가리키는 경로가 바뀐다는 점은 같다. 절대 경로와 상대 경로 모두 사용할 수 있다. 
   14. 실습에서는 `credit cards/T bills.txt`를 `Investments`로 옮긴다. 국채(T bills)는 신용카드가 아니라 투자 상품이라는 이야기 설정을 붙인다. 
   15. 목적지로 디렉터리만 지정하면 파일은 그 안으로 이동하고 원래 이름을 유지한다. 강의자는 목적지 파일 이름까지 명시해 `Investments/T bills.txt`로 옮긴 뒤, `Investments`의 내용을 제출한다. 

16. **`rm`은 파일이나 빈 디렉터리를 삭제하고, 재귀 옵션을 사용하면 디렉터리 안의 내용도 함께 삭제한다.** 
   17. `rm`은 파일이나 빈 디렉터리를 삭제한다. `-r` 또는 `-R` 재귀 옵션을 주면 디렉터리 안의 내용까지 내려가며 삭제한다. 
   18. GUI에서는 디렉터리를 지우면 안의 내용도 함께 없어지는 것이 보통이지만, 명령줄에서는 실수로 많은 파일을 지우지 않도록 일반 `rm`이 디렉터리 삭제를 막는다. 
   19. 실습에서는 `World Bank/private`로 이동해 `password.txt`를 확인한다. 파일에 비밀번호가 평문으로 저장되어 있다는 문제를 발견한다. 
   20. `rm passwords`만 실행하면 디렉터리를 지울 수 없으므로 `rm -R passwords`를 사용해 `passwords` 디렉터리와 그 안의 파일을 삭제한다. 이후 `private`의 내용을 제출한다. 

21. **`cp`는 원본을 남긴 채 파일이나 디렉터리의 복사본을 만든다.** 
   22. `mv`는 옛 경로를 없애고 새 경로로 옮기지만, `cp`는 원본을 유지하면서 새 사본을 만든다. 디렉터리 복사에는 `-R`을 사용할 수 있다. 
   23. 강의자는 `cp`에서는 대문자 `-R`, `rm`에서는 소문자 `-r`을 볼 수 있다고 짚는다. 옵션의 대소문자가 명령마다 다를 수 있다. 
   24. `private/transactions`에는 연도별 거래 파일이 있다. `backups` 디렉터리에는 2020, 2021, 2023 파일은 있지만 2022 백업이 없다는 것을 확인한다. 
   25. 시연에서는 `cp 2020.CSV backups/2020.CSV`를 실행해 2020 파일을 백업 디렉터리에 복사한 뒤, `backups` 내용을 확인해 제출한다. 강의자의 설명은 2022 백업이 없다고 하지만, 실행한 복사 명령은 2020 파일을 대상으로 한다. 

### 3.6 홈 디렉터리와 경로 별칭 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/2722.jpg)

1. **홈 디렉터리는 사용자의 개인 파일을 보관하는 기본 작업 공간이다.** 
   2. Unix 계열 운영체제에서 사용자의 홈 디렉터리는 개인 파일을 저장하는 곳이며, CLI에 처음 로그인할 때 시작 위치가 되는 경우가 많다. World Bank 디렉터리가 홈 안에 있는 이유도 이 때문이다. 
   3. 강의자는 개발 작업을 홈 디렉터리 안에서 하는 것을 권한다. 본인은 `workspace` 디렉터리 아래에 코딩 프로젝트를 모아 두어 컴퓨터 여기저기에 프로젝트가 흩어지지 않도록 한다. 
   4. 홈 디렉터리에서 대부분의 시간을 보내는 것이 좋다. `/bin`, `/etc` 같은 루트 수준의 위치는 시스템이 정해진 용도로 사용하므로, 그곳에 개인 파일을 저장하지 않는 편이 좋다. 

5. **`~`는 홈 디렉터리를 가리키는 별칭이다.** 
   6. 강의자의 Mac 홈 디렉터리는 `/Users/Wags Lane`이며, `~`는 Mac과 Linux에서 홈 디렉터리를 뜻한다. `cd ~`를 입력하면 홈으로 이동할 수 있다. 
   7. `~`는 키보드 숫자 1 왼쪽에 있는 물결표이며, 백틱의 Shift 입력 문자다. 
   8. `~/workspace/names.csv` 같은 경로에서 `~`는 루트 디렉터리가 아니라 홈 디렉터리를 뜻한다. 따라서 이 경로는 홈 안의 `workspace` 디렉터리에 있는 `names.csv`를 가리킨다. 

### 3.7 `grep`과 `find`로 텍스트와 파일 찾기 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/2860.jpg)

1. **`grep`은 파일 안의 텍스트를 찾고, `find`는 파일 자체를 찾는다.** 
   2. `grep`은 문서나 웹페이지에서 `Ctrl+F` 또는 Mac의 `Command+F`로 텍스트를 찾는 기능과 비슷하지만, 더 많은 기능을 제공한다. 
   3. 가장 기본적인 사용법은 `grep hello words.txt`처럼 파일 이름과 찾을 문자열을 지정하는 것이다. 그러면 해당 문자열이 들어 있는 줄을 출력한다. 
   4. 프로그램 로그에는 프로그램이 무엇을 했는지에 관한 정보가 남으며, 문제를 디버깅하거나 수상한 활동을 조사하는 데 쓸 수 있다. 
   5. 실습에서는 World Bank의 `private/logs/2024/0110.log`에서 대문자 `CRITICAL`이 포함된 줄을 `grep`으로 찾는다. 강의자는 결과 네 줄을 확인한 뒤 파일 전체를 `cat`으로 출력해 로그가 매우 길다는 점도 보여준다. 
   6. 한 번에 여러 파일을 검색하려면 `grep`에 파일 이름을 여러 개 전달하면 된다. 
   7. 디렉터리 전체를 검색할 때는 `-r` 재귀 옵션과 디렉터리 경로를 사용한다. `.`은 현재 디렉터리, `..`은 부모 디렉터리, `~`는 홈 디렉터리를 뜻한다. 
   8. 로그 전체에서 `critical`을 찾는 실습에서는 처음에 현재 위치가 `logs`가 아니어서 `.`을 잘못 지정하려다가, `/var/log`를 경로로 사용해 더 많은 결과를 얻는다. 
   9. `find`는 파일 이름으로 파일을 찾으며, 검색할 디렉터리와 `-name` 옵션을 지정한다. 별표 `*`는 임의의 문자열을 대신하는 와일드카드다. 예를 들어 `*.txt`는 이름이 무엇이든 `.txt`로 끝나는 파일을 찾고, `*name*`은 이름 중간에 `name`이 포함된 파일을 찾는다. 

10. **공동 계좌 관련 파일을 이름 패턴으로 찾아 조사한다.** 
   11. 공동 계좌는 소유자가 둘 이상인 계좌다. 실습에서는 사기 활동이 공동 계좌에서 자주 발생한다는 제보를 바탕으로 World Bank의 `public/products` 디렉터리를 검색한다. 
   12. `find`와 이름 패턴을 이용해 이름에 `joint`가 포함된 파일을 찾는다. 이름 앞뒤에는 다른 문자가 더 있을 수 있으므로 와일드카드를 쓴다. 
   13. 검색 결과는 네 개이며, 그 결과를 제출한다.

### 4.1 사용자와 `sudo` 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/3245.jpg)

1. **파일 권한은 컴퓨터에서 어떤 사용자가 무엇을 할 수 있는지를 정한다.** 
   2. Mac과 Linux 같은 Unix 계열 시스템은 여러 사용자를 지원한다. 개인 컴퓨터에는 사용자 한 명만 있을 때가 많지만, 과거에는 한 컴퓨터를 여러 사용자가 함께 쓰는 일이 흔했고 지금도 서버 등에서는 여러 사용자 계정이 사용된다. 
   3. 이 장에서 설명하는 권한은 특정 사용자가 컴퓨터에서 무엇을 할 수 있는지를 뜻한다. 개인 컴퓨터에서는 대체로 자기 계정이 많은 권한을 갖지만, `root` 사용자라는 예외가 있다. 

4. **`sudo`는 한 명령을 높은 권한으로 실행하게 해주지만, 무심코 쓰면 위험하다.** 
   5. 강의자는 `sudo`를 “수도(sudo)”라고 발음하겠다고 농담하며, 발음에 관한 다른 사람들의 설명보다 자신의 발음을 고수하겠다고 말한다. 
   6. `sudo`는 평소 권한으로 할 수 없는 작업을 가능하게 한다. 농담으로 “샌드위치를 만들어줘”에 “아니, `sudo`로 샌드위치를 만들어줘”라고 말하는 예를 든다. 
   7. `sudo`는 `super user do`에서 온 말이며, 명령을 실행할 때 일시적으로 슈퍼 사용자, 보통 `root` 사용자 권한으로 동작하게 한다. 
   8. `sudo`를 쓰면 제한 없는 권한을 얻을 수 있어 시스템을 손상할 위험이 있다. 모든 명령 앞에 습관적으로 붙이면 안 된다. 
   9. `who am I`는 현재 로그인한 사용자를 보여주고, `sudo who am I`는 비밀번호를 입력하게 한 뒤 권한이 상승한 사용자로 명령을 실행한다. 비밀번호 확인은 보안 절차다. 

### 4.2 권한 문자열 읽기 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/3371.jpg)

1. **권한 문자열은 파일 종류와 소유자·그룹·그 밖의 사용자가 가진 권한을 나타낸다.** 
   2. Unix 계열 시스템의 파일과 디렉터리에는 권한이 붙는다. 권한은 **누가** 접근할 수 있는지와 **무엇을** 할 수 있는지로 나눠 이해한다. 
   3. 권한 문자열은 10자리로 나타난다. 첫 글자는 `d` 또는 `-`이며, `d`는 디렉터리, `-`는 파일을 뜻한다. 
   4. 이어지는 세 글자 `rwx`는 소유자의 읽기(read), 쓰기(write), 실행(execute) 권한이다. 소유자는 보통 파일을 만든 사용자지만, 수동으로 바꿀 수 있다. 
   5. 권한이 있으면 글자를 표시하고 없으면 `-`로 표시한다. `rwx`는 세 권한 모두 있음, `r-x`는 읽기와 실행은 가능하지만 쓰기는 불가, `r--`는 읽기만 가능하다는 뜻이다. 
   6. `rwx` 세 글자 묶음은 그룹 권한과 그 밖의 모든 사용자 권한을 위해 두 번 더 반복된다. 
   7. `drwxr-xr--`는 디렉터리이며, 소유자는 읽기·쓰기·실행, 그룹은 읽기·실행, 그 밖의 사용자는 읽기만 가능하다는 뜻이다. 

8. **권한의 세 주체는 소유자, 그룹, 그 밖의 사용자이며, 세 종류의 동작은 읽기·쓰기·실행이다.** 
   9. 권한 문자열은 `d rwx rwx rwx` 형태로 볼 수 있다. 첫 글자는 디렉터리인지 파일인지, 나머지 아홉 글자는 권한을 나타낸다. 
   10. 첫 번째 `rwx`는 소유자, 두 번째는 그룹, 세 번째는 그 밖의 사용자 권한이다. 예를 들어 `drwxrwxrwx`는 디렉터리이며 세 주체 모두 읽기·쓰기·실행이 가능하다는 뜻이다. 
   11. 권한 문자가 빠진 자리는 `-`로 표시한다. 예를 들어 `rw-`는 읽고 쓸 수 있지만 실행할 수 없다는 의미다. 
   12. 소유자는 파일을 소유한 사용자이며, 본인이 파일 소유자라면 소유자 권한이 적용된다. 
   13. 그룹 권한은 여러 사용자로 이루어진 그룹에 적용된다. 개인 컴퓨터에서 로컬 개발을 할 때는 그룹 권한을 자주 다루지 않을 수 있다. 
   14. 그 밖의 사용자는 소유자나 해당 그룹에 속하지 않는 나머지 사용자다. 이들에게 읽기·쓰기·실행 권한을 주면 누구든 해당 작업을 할 수 있으므로, 네트워크로 접근 가능한 웹 서버에서는 특히 주의해야 한다. 
   15. 강의 범위는 웹 서버 보안의 모든 결과를 설명하는 것이 아니라, 개인 컴퓨터에서 개발하고 도구를 설치할 때 필요한 권한 이해에 초점을 둔다. 퀴즈에서는 권한 문자열의 마지막 `rwx` 묶음이 그 밖의 사용자를 뜻한다는 점 등을 확인한다. 

16. **권한을 묻는 문제에서는 각 세 묶음을 주체별로 나눠 읽는다.** 
   17. “모두가 읽을 수 있는 권한”을 묻는 문제는 소유자·그룹·그 밖의 사용자 순서로 각 묶음을 살펴본다. 
   18. “소유자가 실행할 수 있는 권한”을 묻는 문제에서는 첫 번째 `rwx` 묶음에 `x`가 있는지 확인한다. 제시된 보기 중 소유자 권한에 실행이 포함된 항목을 고른다. 

### 4.3 `chmod`로 권한 바꾸기 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/3713.jpg)

1. **`chmod`는 파일과 디렉터리의 권한을 바꾼다.** 
   2. `chmod`는 `change mode`의 줄임말이며, 터미널에서 자주 쓰는 권한 변경 명령이다. 이름이 직관적이지 않다는 점은 `cat`과 비슷하다고 강의자는 말한다. 
   3. 보안 조사 실습에서는 `ls -l private`로 `private` 안의 파일과 디렉터리 권한을 긴 형식으로 출력한다. `-l`을 쓰면 권한 정보가 왼쪽에 표시된다. 
   4. `private` 디렉터리와 그 안의 모든 항목에 대해 소유자만 읽기·쓰기·실행할 수 있고, 그룹과 그 밖의 사용자는 아무 권한도 갖지 않도록 설정한다. 
   5. `chmod -R`은 디렉터리와 그 안의 항목에 변경을 재귀적으로 적용한다. 예시 명령은 소유자에게 `rwx`, 그룹과 그 밖의 사용자에게는 권한을 주지 않는 설정이다. 
   6. 변경 뒤 `ls -l`로 권한이 바뀌었는지 확인하고, 과제에는 디렉터리 자체의 10자리 권한 문자열을 제출한다. 

7. **읽기·쓰기·실행 권한은 프로그램이 파일을 다루는 방식과 연결된다.** 
   8. `cat`, `head`, `tail`, `grep` 등으로 파일 내용을 읽는 것은 읽기 권한이 필요한 작업이다. 파일을 바꾸려면 쓰기 권한이 필요하다. 
   9. 실행 권한은 파일을 프로그램처럼 실행할 수 있는지를 뜻한다. 파일 안의 데이터를 CPU가 명령으로 처리하도록 할 수 있는 권한이다. 
   10. 신뢰하지 않는 파일을 실행하지 못하게 하는 권한은 악성 코드가 실행되는 것을 막는 보호 수단 중 하나다. 

### 4.4 셸 스크립트와 실행 권한 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/3914.jpg)

1. **셸 스크립트는 셸 명령을 적은 텍스트 파일이며, 실행하려면 적절한 인터프리터와 권한이 필요하다.** 
   2. `.sh` 확장자를 가진 파일은 보통 셸 스크립트다. 셸에서 실행해온 명령을 텍스트 파일에 모아두고, 셸 인터프리터가 그 명령을 읽어 실행한다. 확장자가 반드시 `.sh`여야 하는 것은 아니다. 
   3. Zsh나 Bash에서 프로그램을 실행하려면 일반적으로 프로그램의 경로를 입력한다. 프로그램이 현재 디렉터리에 있다면 현재 디렉터리를 뜻하는 `.`을 명시해야 한다. 

4. **`chmod +x`는 실행 권한이 없어 실행되지 않는 스크립트의 문제를 해결하는 흔한 방법이다.** 
   5. 실습에서는 `World Bank/private/bin`의 의심스러운 `gen_ids` 스크립트를 찾는다. 
   6. `chmod -x gen_ids`로 실행 권한을 제거한 뒤 실행을 시도하면 `permission denied`가 발생한다. 이는 현재 사용자에게 실행 권한이 없기 때문이다. 
   7. `chmod +x gen_ids`로 실행 권한을 다시 부여하면 스크립트를 실행할 수 있다. 
   8. 온라인에서 내려받은 스크립트나 직접 만든 파일을 실행할 때 `permission denied`가 나온다면, 실행 권한이 빠졌는지 확인하는 것이 좋다. 강의자는 이런 경우 대부분 `chmod +x filename`으로 해결된다고 설명한다. 
   9. 실행 후 스크립트 출력 결과를 과제란에 제출한다. 

### 4.5 `root` 사용자와 위험한 명령 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/4033.jpg)

1. **`root`는 시스템의 거의 모든 작업을 할 수 있는 슈퍼 사용자다.** 
   2. 강의자는 앞서 언급한 XKCD 만화를 다시 떠올리며 `root` 사용자를 설명한다. 
   3. `root`는 시스템의 모든 것에 접근할 수 있고, 거의 어떤 작업이든 할 수 있는 슈퍼 사용자다. 보통 `sudo`를 사용하면 한 명령을 `root` 권한으로 실행한다. 
   4. 셸 세션 전체를 계속 `root`로 전환하는 것도 가능하지만, 보통은 필요한 명령 하나만 잠시 높은 권한으로 실행하는 편이 낫다. 

5. **높은 권한으로 실행하는 명령은 시스템 전체를 망가뜨릴 수 있으므로 내용을 이해해야 한다.** 
   6. `rm -rf`는 강제로 재귀 삭제하는 명령이다. `rm -rf /`는 시스템 파일을 포함해 컴퓨터의 모든 파일을 지울 수 있으므로 실행하면 안 된다. 
   7. 일부 시스템은 루트 삭제를 막는 보호 기능을 두며, 실제 실행에는 `--no-preserve-root` 같은 옵션이 더 필요할 수 있다. 강의자는 그런 예외가 있더라도 핵심은 `sudo rm -rf /` 같은 명령을 실행하지 말라는 것이라고 강조한다. 
   8. 퀴즈에서는 슈퍼 사용자의 실제 계정 이름이 `root`임을 확인한다. `root`는 사용자이며, 슈퍼 사용자는 높은 권한을 가진 사용자 유형을 뜻한다. 
   9. `sudo rm -rf /`가 실행되면 운영체제가 작동하는 데 필요한 파일까지 삭제될 수 있다. 다만 일부 시스템에는 추가 보호 장치가 있어 실행 결과가 달라질 수 있다. 

### 4.6 `chown`으로 소유자 바꾸기 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/4278.jpg)

1. **`chmod`가 권한을 바꾸는 명령이라면, `chown`은 파일이나 디렉터리의 소유자를 바꾸는 명령이다.** 
   2. 사용자는 자신이 소유한 파일의 권한을 바꿀 수 있지만, 다른 사용자의 파일 권한을 마음대로 바꿀 수는 없다. 소유자 변경에는 `chown`을 사용한다. 
   3. 실습에서는 `private/contacts`와 그 안의 `emergency.txt`를 확인한다. 파일에는 직원의 긴급 연락처처럼 보이는 개인 정보가 들어 있다. 
   4. 이 디렉터리는 개인 사용자인 Wags Lane보다 `root`가 소유하는 편이 적절하다는 설정으로, `chown`을 이용해 디렉터리 전체의 소유자를 바꾼다. 
   5. 재귀 옵션을 적용하면 `contacts` 디렉터리와 그 안의 내용도 함께 소유자가 바뀐다. 이 작업에는 `sudo` 비밀번호를 입력한다. 
   6. 확인할 때는 `ls -l` 출력에서 `contacts` 디렉터리에 해당하는 줄을 기준으로 소유자와 권한을 본다. 

7. **소유자가 `root`로 바뀌면 일반 사용자에게 삭제 권한이 없을 수 있다.** 
   8. 삭제 실습 전에는 `contacts`의 권한이 `drwx`로 시작하고 소유자가 `root`이며, 현재 로그인한 사용자는 `root`가 아닌지 확인한다. 
   9. `rm -R contacts`로 삭제를 시도하면 권한이 없어 실패한다. 일반 사용자는 소유자가 아니며, 그룹에도 삭제에 필요한 권한이 없기 때문이다. 
   10. `sudo`를 붙여 `root` 권한으로 삭제하면 디렉터리를 제거할 수 있다. 이후 `private` 디렉터리에서 `ls`를 실행해 결과를 제출한다. 

## 5. 프로그램과 셸 환경 설정 

이 장에서는 컴파일된 프로그램과 인터프리터가 필요한 프로그램을 비교한 뒤, 셸 설정 파일과 환경 변수, 특히 `PATH`를 다룬다.

### 5.1 컴파일 프로그램과 인터프리터 프로그램 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/4515.jpg)

1. **프로그램은 컴퓨터가 실행할 명령의 묶음이며, 크게 컴파일된 프로그램과 인터프리터가 필요한 프로그램으로 나뉜다.** 
   2. 컴파일된 프로그램은 보통 C, Rust, Go 같은 언어로 작성한 뒤 기계어에 가까운 이진 파일로 변환한다. 실행할 때 다른 프로그램의 해석에 의존하지 않고 하드웨어에서 직접 실행될 수 있다. 
   3. 인터프리터 방식의 프로그램은 코드를 읽고 실행해주는 별도 프로그램이 필요하다. Python, Ruby, JavaScript, 셸 스크립트가 그 예다. 
   4. 컴파일된 프로그램은 셸에 프로그램 이름을 입력해 실행할 수 있지만, Python 코드 파일은 `python` 같은 인터프리터를 지정해야 한다. 
   5. 실행 파일(executable)은 프로그램이라는 명사로도, 실행할 수 있다는 뜻의 형용사로도 쓰인다. 컴파일된 프로그램은 컴퓨터 CPU가 실행하는 기계어 형식이며, 사람이 읽기 어렵고 이진 데이터로 표현된다. 이를 바이너리라고도 부른다. 
   6. 인터프리터 프로그램도 결국 CPU에서 실행되지만, 코드 자체가 하드웨어용 기계어로 변환된 것은 아니다. 그래서 인터프리터가 필요하고, 보통 컴파일 프로그램보다 느릴 수 있지만 특정 하드웨어 구조에 맞춰 다시 컴파일하지 않아도 되는 등 플랫폼 간 이동이 쉬울 수 있다. 

7. **Windows의 `.exe`와 셸·Python 스크립트는 서로 다른 실행 방식을 보여주는 예다.** 
   8. Windows 게임에서 자주 보는 `.exe`는 대개 하드웨어에서 실행되도록 컴파일된 프로그램이다. Linux와 Mac에서는 `.exe` 확장자를 보통 사용하지 않지만, 컴파일된 프로그램 자체는 있다. 
   9. 셸 스크립트와 Python 스크립트는 인터프리터 프로그램의 예다. Python 스크립트를 실행할 때는 보통 `python main.py`처럼 Python 인터프리터를 명시한다. 
   10. 셸 스크립트는 인터프리터를 직접 적지 않고 실행할 수도 있지만, 내부적으로는 여전히 Zsh나 Bash 같은 셸 인터프리터가 사용된다. 
   11. `which sh`로 `sh` 실행 파일의 경로를 확인한 뒤 `cat`으로 내용을 보면, 이진 데이터가 텍스트처럼 표시되어 대부분 알아보기 어려운 결과가 나온다. 
   12. `sh` 실행 파일은 컴파일된 프로그램이지만, 앞서 본 `gen_ids` 같은 셸 스크립트는 일반 텍스트다. 둘 다 실행할 수 있는 프로그램이지만, 스크립트는 인터프리터가 있어야 실행된다. 
   13. 컴파일된 실행 파일은 인터프리터를 따로 지정하지 않고 실행할 수 있다. 셸 스크립트와 Python 스크립트는 각각 셸 또는 Python 인터프리터가 필요하다. 

### 5.2 Shebang과 셸 종류 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/4838.jpg)

1. **Shebang은 스크립트 첫 줄에 인터프리터 경로를 적어 실행 시 사용할 프로그램을 알려준다.** 
   2. 실행 파일 경로를 셸에 입력하면 프로그램을 실행할 수 있지만, 인터프리터가 필요한 파일은 인터프리터를 따로 지정해야 할 수 있다. 
   3. 스크립트 첫 줄에 인터프리터를 적는 **shebang**을 넣으면, 셸에서 스크립트 파일을 직접 실행할 때 어떤 인터프리터를 쓸지 알려줄 수 있다. 
   4. 예를 들어 Python 3 인터프리터를 지정하면, 매번 `python3 main.py`라고 쓰지 않고 `main.py`를 직접 실행할 수 있다. 
   5. 실습에서는 `private/bin/gen_ids`의 내용을 `cat`으로 확인해 첫 줄에 있는 shebang을 제출한다. 

6. **`sh`, Bash, Zsh는 서로 관련이 있지만 같은 셸은 아니다.** 
   7. Windows WSL Ubuntu에서는 보통 Bash를 사용하고, Mac에서는 보통 Zsh를 사용한다. 오래된 Mac은 Bash일 수도 있으며, 사용자 설정에 따라 달라질 수 있다. 
   8. 일반적인 웹 개발에서는 Bash와 Zsh의 차이가 크게 드러나지 않을 수 있지만, 복잡한 스크립트를 많이 작성하면 두 셸이 서로 다른 언어이므로 차이가 나타난다. 
   9. `sh`는 Bourne shell의 약자로, 초기 Unix 셸이다. POSIX 규칙을 따르며, 스크립트가 일정한 문법과 동작을 지키도록 한다. 
   10. `sh`는 기본적인 기능 위주라 편의 기능이 많지 않다. 복잡한 스크립트를 작성하면 코드가 길고 장황해질 수 있다. 
   11. Bash는 “Bourne Again Shell”의 약자이며 Linux에서 흔히 쓰인다. Zsh는 Z Shell이며 Mac에서 흔히 쓰인다. 두 셸 모두 `sh`에 여러 기능을 더했지만, 서로 다른 셸이다. 
   12. Bash와 Zsh는 `sh`와 호환되므로 기본적인 `sh` 스크립트를 실행할 수 있다. 강의에서는 Bash와 Zsh가 `sh`의 상위 집합(superset)이라고 정리한다. 

### 5.3 셸 설정 파일과 환경 변수 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/5101.jpg)

1. **셸 설정 파일은 새 셸 세션이 시작될 때 자동 실행되어 환경을 설정한다.** 
   2. Bash와 Zsh는 새 셸 세션을 열 때 자동으로 실행되는 설정 파일을 갖는다. 설정 파일에서 별칭, 함수, 환경 변수 등을 지정할 수 있다. 
   3. 설정 파일은 컴퓨터를 켤 때 자동 실행할 프로그램을 지정하는 것과 비슷하게, 셸을 열 때 자동으로 실행할 명령을 적어두는 곳이다. 
   4. 설정 파일은 사용자별로 홈 디렉터리에 있으며 기본적으로 숨김 파일이다. `ls -a`는 숨김 파일을 포함해 표시한다. 
   5. 강의자의 `.zshrc`는 파일 이름 앞에 점이 붙어 숨김 파일이며, 새 Zsh 셸을 열 때 실행된다. 
   6. 조사 실습에서는 자동 실행되는 셸 설정 파일을 확인하기 위해 `.zshrc`를 Nano로 열고, 맨 아래에 `echo hello from the shell`을 추가한다. 저장은 `Ctrl+O`, 종료는 `Ctrl+X`로 한다. 
   7. 터미널을 닫고 새로 열었을 때 `hello from the shell`이 표시되면 올바른 설정 파일을 수정한 것이다. 강의자는 새 Ghostty 탭을 열어 메시지가 나오는 것을 확인한다. 
   8. 이후 추가한 줄을 설정 파일에서 지우고 저장한다. 새 탭에서 메시지가 더 이상 나오지 않는 것으로 삭제를 확인한다. 
   9. 설정 파일을 바꾼 뒤 새 셸을 여는 이유는 설정 파일이 새 셸 세션을 시작할 때 자동 실행되기 때문이다. 

10. **환경 변수는 셸에서 실행되는 프로그램들이 읽을 수 있는 값이다.** 
   11. 셸에서만 쓰는 일반 변수와 달리, 환경 변수는 해당 셸에서 실행되는 프로그램들이 접근할 수 있다. 프로그램 설정에 환경 변수를 사용하는 경우가 많다. 
   12. `env` 명령은 현재 설정된 환경 변수 목록을 보여준다. 다만 개인 키 같은 비밀 정보가 포함될 수 있으므로 강의자는 화면에 전체 출력을 표시하지 않는다. 
   13. 환경 변수를 만들 때는 `export`를 사용한다. 관례상 환경 변수 이름은 대문자로 쓰는 경우가 많다. 
   14. 실습에서는 `private/bin/warn.sh`를 확인한다. 스크립트는 `WARN_MESSAGE`와 `WARN_FROM_NAME`에 해당하는 환경 변수 값을 사용한다. 강의자가 설명하는 변수 이름은 소문자 형태로 들리는 부분이 있으나, 핵심은 스크립트가 환경 변수 값을 읽는다는 것이다. 
   15. 변수를 설정하지 않고 스크립트를 실행하면 메시지와 발신자 부분이 비어 있다. 값을 설정한 뒤 실행하면 “the auditor is here”, “your worst nightmare”라는 문구가 출력된다. 
   16. 변수 설정 과정에서 Zsh가 `bad assignment` 오류를 내자 강의자는 입력을 수정한다. 셸 변수 대입에서 `=` 앞뒤에 공백을 넣지 않아야 한다는 점을 확인한다. 

### 5.4 `PATH`의 의미와 임시 변경 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/5406.jpg)

1. **`PATH`는 프로그램을 이름만 입력해 실행할 수 있도록 셸이 찾아볼 디렉터리 목록이다.** 
   2. 강의자는 `chmod +x`, 환경 변수, 파일 경로가 과정에서 반복해 쓰이는 핵심 개념이라고 강조한다. 특히 개발 경력이 오래된 사람도 `PATH`와 설치 프로그램 위치에서 혼란을 겪는다고 말한다. 
   3. 어떤 환경 변수는 특정 프로그램이나 여러 프로그램이 관례적으로 읽는다. `PATH`는 그중 하나로, 여러 디렉터리의 경로 목록을 저장한다. 
   4. `PATH`에 포함된 디렉터리에 있는 실행 파일은 전체 경로를 입력하지 않고 이름만으로 실행할 수 있다. 
   5. `cat`의 위치를 `which cat`으로 확인하면 `/bin/cat`이 나온다. `/bin`이 `PATH`에 들어 있기 때문에 셸이 `cat`을 찾아 실행한다. 
   6. 어디서든 프로그램 이름만 입력해 실행하고 싶다면, 해당 프로그램이 들어 있는 디렉터리가 `PATH`에 있어야 한다. 
   7. `PATH`에는 여러 절대 경로가 들어 있고, 경로들은 콜론으로 구분된다. 목록에 있는 디렉터리 안의 실행 파일은 권한이 있는 경우 이름만으로 실행할 수 있다. 

8. **프로그램이 설치된 뒤에도 `command not found`가 나올 수 있으며, 설치 위치가 `PATH`에 있는지 확인해야 한다.** 
   9. 프로그램이 `PATH`에 없는 디렉터리에 설치되면 셸은 이름만으로 프로그램을 찾지 못해 `command not found`를 표시할 수 있다. 
   10. 실습에서는 `PATH`를 빈 문자열로 설정해 프로그램을 전체 경로로만 실행할 수 있게 만든다. 이 변경은 현재 셸 세션에만 적용되며, 새 셸을 열면 기본값으로 돌아온다. 
   11. `PATH`를 비우면 `ls`를 찾지 못해 실행할 수 없다. 반면 셸에 내장된 일부 명령은 `PATH` 검색이 필요하지 않아 계속 동작할 수 있다. 
   12. 프로그램 설치 때는 설치 프로그램이나 패키지 관리자가 출력하는 안내를 확인해야 한다. 설치 경로가 `PATH`에 없으면 그 디렉터리를 `PATH`에 추가할 수 있다. 
   13. 강의자는 설치 명령의 출력을 대충 넘긴 뒤 프로그램을 실행해 오류를 만나는 일이 흔하다고 말한다. 오류가 나면 바로 검색하기보다 설치 안내와 실제 설치 위치를 먼저 확인하는 것이 좋다. 

### 5.5 `PATH`를 현재 세션에 추가하고 영구 설정하기 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/5825.jpg)

1. **현재 셸에 `PATH`를 추가하면 새 셸을 열기 전까지 다른 위치에서도 프로그램을 실행할 수 있다.** 
   2. 셸을 다시 시작하면 앞서 임시로 비운 `PATH`가 기본값으로 돌아온다. 
   3. World Bank의 `private/bin`에는 어디서든 실행하고 싶은 프로그램이 있다. 강의자는 해당 디렉터리로 이동해 `pwd`로 절대 경로를 확인한다. 
   4. `export PATH=$PATH:<새 디렉터리>`와 같은 형태로 기존 `PATH` 뒤에 콜론과 새 디렉터리를 붙인다. 기존 값을 유지하지 않고 새 디렉터리만 설정하면 다른 경로를 잃게 된다. 
   5. World Bank 디렉터리에서 벗어나 홈 디렉터리로 이동한 뒤 `worldbank.sh`를 실행한다. 프로그램 디렉터리가 `PATH`에 추가되었기 때문에 현재 디렉터리가 달라도 파일 이름으로 실행할 수 있다. 
   6. 실습 프로그램은 이름과 이메일을 입력받는다. 강의자는 이메일처럼 보이는 값을 입력하고, 전체 상호작용을 복사해 제출한다. 

7. **`PATH` 설정을 셸 설정 파일에 기록하면 새 세션을 열어도 유지된다.** 
   8. 앞서 추가한 `PATH`는 현재 셸에만 적용되므로 새 터미널을 열면 사라진다. 실제로 새 세션에서 `worldbank.sh`를 실행하자 `command not found`가 나타난다. 
   9. `.zshrc` 같은 설정 파일은 `PATH`를 영구적으로 수정할 때 흔히 쓰인다. 강의자는 `.zshrc`를 열어 끝에 앞서 사용한 `export PATH=$PATH:<World Bank private/bin 경로>` 명령을 추가한다. 
   10. 변경을 적용하려면 새 셸 세션을 열거나 `source .zshrc`를 실행해 설정 파일을 다시 읽게 할 수 있다. 
   11. 다시 `worldbank.sh`를 실행해 성공을 확인한다. 설정 파일에 추가했기 때문에 새 세션에서도 사용할 수 있게 된다. 
   12. 퀴즈의 핵심은 `PATH`를 설정 파일에 저장하면 프로그램이 현재 세션에만 제한되지 않고 이후 셸 세션에서도 사용할 수 있다는 것이다. 
   13. 프로그램을 설치해 일상적으로 사용하려면 `.zshrc`, `.bashrc`, 일부 Linux 배포판의 `.bash_profile` 같은 셸 설정 파일을 편집할 수 있다. 

## 6. 명령의 도움말과 인수 

이 장에서는 프로그램 문서와 옵션을 확인하는 방법, 플래그와 위치 인수의 차이를 설명하고 `wc`, `mv`, `curl`을 예로 든다.

### 6.1 `man`으로 매뉴얼 읽기 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/6011.jpg)

1. **`man`은 프로그램 사용법을 보여주는 매뉴얼 도구다.** 
   2. `man`은 manual의 줄임말이며, `man 명령어이름` 형태로 사용한다. 모든 프로그램에 매뉴얼이 있는 것은 아니지만 전통적인 Unix 명령 중에는 매뉴얼이 있는 것이 많다. `man man`은 매뉴얼 도구 자체의 설명을 보여준다. 
   3. 매뉴얼은 `less`와 비슷한 대화형 화면으로 열린다. Enter로 내용을 내려가고 `q`로 종료할 수 있다. 
   4. 매뉴얼을 처음부터 끝까지 읽기보다, 필요한 옵션을 찾을 때 참조하는 방식이 일반적이다. 강의자는 Neovim이나 Bash 매뉴얼을 재미 삼아 읽는 사람도 있지만 대부분은 필요한 내용을 찾아본다고 말한다. 
   5. 예를 들어 `ls` 매뉴얼에서 `/`를 누른 뒤 `-R`을 검색하면 해당 옵션의 설명을 찾을 수 있다. `n`을 누르면 다음 검색 결과로 이동하고 `q`로 나올 수 있다. 

6. **`grep` 매뉴얼은 명령의 동작과 옵션을 확인하는 실전 예다.** 
   7. 시스템 관련 작업에서 `grep`은 강력하지만 처음에는 사용법이 헷갈릴 수 있으므로 `man grep`으로 매뉴얼을 열어본다. 
   8. 매뉴얼에는 `grep`, `egrep`, `fgrep` 같은 이름과 명령에 전달할 수 있는 여러 인수의 문법이 표시된다. 이 과정에서는 복잡한 문법 전체를 다루지는 않는다. 
   9. `grep`은 입력 파일에서 주어진 패턴과 일치하는 줄을 선택한다. 기본적으로 정규식 패턴이 줄의 내용과 일치하면 그 줄을 표준 출력으로 내보내며, 빈 패턴은 모든 줄과 일치한다. 
   10. 기본 `grep`은 단순 패턴과 기본 정규식을 다루며, `egrep`은 확장 정규식을, `fgrep`은 고정된 패턴을 다룬다고 매뉴얼이 설명한다. 강의자는 `fgrep`이 더 빠르지만 고정 패턴만 처리한다고 소개한다. 
   11. 매뉴얼에서 `-v`를 찾아보면 일치하지 않는 줄을 선택하는 `invert match` 옵션임을 알 수 있다. 
   12. 옵션 문제에서는 `-c`가 개수, `-i`가 대소문자 무시, `-R`이 재귀 검색임을 확인한다. 선택지 중 존재하지 않는 `-t`가 잘못된 옵션이다. 

### 6.2 플래그와 옵션 조합 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/6237.jpg)

1. **플래그는 명령의 동작을 바꾸는 선택 옵션이다.** 
   2. `ls -l`은 긴 형식으로 파일을 보여주고, `ls -a`는 숨김 파일을 포함해 보여준다. 이런 옵션을 플래그라고 한다. 
   3. 여러 플래그는 `ls -Al`, `ls -la`, `ls -l -a`처럼 함께 쓸 수 있다. 같은 문자 옵션을 묶을 때는 각 글자 앞에 대시를 반복해서 붙이지 않아도 된다. 
   4. 명령이 어떤 플래그를 지원하고 어떤 뜻으로 쓰는지는 명령을 만든 개발자가 정한다. `-r`이 흔히 재귀를 뜻하더라도 모든 명령에서 같은 의미라고 가정해서는 안 된다. 

5. **짧은 옵션과 긴 옵션은 상황에 따라 선택한다.** 
   6. 한 글자로 된 옵션은 보통 대시 하나를 붙인다. 긴 형태의 옵션은 대시 두 개를 쓰는 경우가 많다. 예를 들어 `-a`와 `--text`가 짝을 이룰 수 있다. 
   7. 터미널에서 명령을 직접 입력할 때는 짧은 옵션이 편리하다. 
   8. 다른 사람이 읽을 스크립트를 작성할 때는 `--text`처럼 뜻이 분명한 긴 옵션을 쓰면 의도가 잘 드러난다. 

### 6.3 `wc`와 위치 인수 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/6364.jpg)

1. **`wc`는 파일의 줄·단어·문자·바이트 수를 세며, 원하는 수치를 플래그로 고른다.** 
   2. 조사 중에는 변조된 파일을 찾기 위해 각 파일의 바이트 수를 알아야 하는 상황이 생긴다. 이때 `wc`(word count)를 사용한다. 
   3. `man wc`에서 바이트 수를 출력하는 옵션을 찾으면 `-c`를 확인할 수 있다. 
   4. `wc`는 기본적으로 단어 수를 세며, 옵션에 따라 줄·문자·바이트 수를 출력한다. 강의자는 `PR ideas.txt`에서 바이트 수가 1,098이라고 확인한다. 

5. **플래그의 순서는 대체로 바뀔 수 있지만, 위치 인수의 순서는 의미가 있다.** 
   6. `ls -la`와 `ls -al`처럼 플래그의 순서는 보통 달라도 같은 결과를 낸다. 
   7. **위치 인수(positional argument)**는 명령 뒤에서 순서에 따라 의미가 정해지는 값이다. Python의 일반 인수와 비슷하며, 플래그는 키워드 인수와 비슷하다고 생각할 수 있다. 
   8. `ls`는 현재 디렉터리의 내용을 보여주지만, 첫 번째 위치 인수로 `World Bank`를 전달하면 그 디렉터리의 내용을 보여준다. 
   9. 실습에서는 World Bank의 공개 디렉터리에 있는 `key.txt`를 읽는다. 이 파일에는 개인 RSA 키가 들어 있어 위험한 정보로 묘사된다. 
   10. `mv`에는 원본 경로와 목적지 경로라는 두 위치 인수가 순서대로 들어간다. 파일을 다른 위치로 옮긴 뒤 `private` 디렉터리의 내용을 확인해 제출한다. 

### 6.4 `--help`와 `curl` 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/6617.jpg)

1. **많은 CLI 도구는 `--help`, `-h` 또는 `help`로 간단한 사용법을 보여준다.** 
   2. 명령줄 도구는 보통 `-h`, `--help`, `help` 중 하나로 도움말을 제공한다. 
   3. 도움말은 전체 매뉴얼보다 짧고 찾기 쉬운 경우가 많다. 특히 기본 Unix 명령이 아닌 별도 프로그램은 매뉴얼 항목보다 함께 제공되는 도움말을 찾기 쉬울 수 있다. 

4. **`curl`은 명령줄에서 네트워크 요청을 보내는 도구다.** 
   5. 보안 감사에서는 이 컴퓨터가 승인된 시스템에만 네트워크 요청을 보내는지 확인해야 하며, 이를 위해 `curl`을 사용할 수 있다. 
   6. 실습에서는 `curl`의 도움말을 출력한다. 강의자는 `--help`를 시도해 간단한 사용법을 확인하고, 매뉴얼보다 짧은 안내가 표시되는 것을 보여준다. 
   7. 도움말을 출력하는 데 사용한 명령을 과제란에 제출한다. 

## 7. 프로그램의 상태와 입출력 

이 장에서는 프로그램의 성공·실패를 나타내는 종료 코드, 표준 입출력 스트림과 리디렉션, 파이프, 실행 중인 프로그램을 중단하는 방법을 다룬다.

### 7.1 종료 코드 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/6731.jpg)

1. **종료 코드는 프로그램 실행이 성공했는지 실패했는지를 다른 프로그램에 알려준다.** 
   2. 종료 코드는 반환 코드(return code) 또는 상태 코드(status code)라고도 하며, 프로그램이 실행을 마친 뒤 성공 여부를 전달한다. 
   3. `0`은 성공이고, `0`이 아닌 값은 오류를 뜻한다. `0`과 `1`이 흔하지만 다른 숫자도 쓰인다. 
   4. 사람이 터미널에서 명령을 직접 실행할 때는 화면 출력만 봐도 성공 여부를 알 수 있는 경우가 많다. 하지만 자동화에서는 프로그램이 성공했는지 판단하는 데 종료 코드가 중요하다. 
   5. 한 프로그램이 다른 프로그램을 실행하는 경우에도 종료 코드를 확인할 수 있다. 예를 들어 서버를 감시하는 프로그램은 서버가 오류로 종료했는지 확인한 뒤 재시작 여부와 처리 방법을 결정할 수 있다. 

6. **셸의 `$?`는 직전에 실행한 프로그램의 종료 코드를 담는다.** 
   7. 홈 디렉터리의 내용을 `ls`로 확인한 뒤 `echo $?`를 실행하면 앞선 명령의 종료 코드를 출력한다. 성공한 경우에는 `0`이 나온다. 
   8. 존재하지 않는 파일을 `ls`로 찾으면 오류 메시지가 나오며 종료 코드가 0이 아닌 값으로 바뀐다. 강의자의 시연에서는 `1`이 출력된다. 
   9. 필요한 인수나 설정이 없는 경우에도 프로그램은 오류 코드로 종료할 수 있다. World Bank의 `warn.sh`는 필요한 환경 변수가 없으면 오류 메시지를 출력하고 종료한다. 
   10. 이 스크립트는 종료 코드 `69`를 반환한다. 강의자는 스크립트 내용을 확인해 작성자가 그 값을 직접 지정했음을 보여준다. 

### 7.2 표준 출력과 표준 오류, 리디렉션 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/7003.jpg)

1. **표준 출력(stdout)은 프로그램이 기본적으로 결과를 내보내는 데이터 흐름이다.** 
   2. 수강자는 이미 강의 전체에서 표준 출력을 사용해왔다. 표준 출력은 `stdout`이라고도 하며, 프로그램이 기본적으로 결과를 보내는 데이터 스트림이다. 
   3. 터미널에서 실행할 때는 보통 이 텍스트가 화면에 표시된다. 하지만 표준 출력을 다른 곳으로 돌릴 수도 있다. 
   4. 대부분의 프로그래밍 언어에는 표준 출력에 내용을 쓰는 기본 방법이 있다. Python의 `print`, 셸의 `echo`가 그 예다. 
   5. 실습에서는 World Bank의 `private/transactions/2020.CSV`에서 `Marshall`이 들어 있는 줄을 `grep`으로 찾아 표준 출력에 표시한다. 

6. **표준 오류(stderr)는 오류 메시지를 보내는 별도 데이터 흐름이다.** 
   7. `stderr`도 프로그램이 데이터를 내보내는 스트림이지만, 관례상 오류나 문제 관련 메시지를 보내는 데 쓴다. 
   8. 표준 출력과 표준 오류를 나누면 프로그램을 호출한 쪽에서 성공 결과와 오류 메시지를 서로 다른 곳으로 보낼 수 있다. 
   9. 터미널에서는 표준 출력과 표준 오류가 모두 화면에 표시되므로, 겉으로만 보면 어느 스트림에서 온 것인지 구분하기 어려울 수 있다. 
   10. 셸에서는 출력 스트림을 파일 등 다른 위치로 리디렉션할 수 있다. 

11. **`>`는 표준 출력을, `2>`는 표준 오류를 다른 위치로 보낸다.** 
   12. `echo hello world > hello.txt`처럼 쓰면 문장이 터미널에 표시되지 않고 `hello.txt`에 저장된다. `ls -l`로 파일을 확인하고 `cat`으로 내용을 읽을 수 있다. 
   13. 서버 로그를 나중에 확인하기 위해 파일로 저장하는 것은 백엔드 개발에서 흔한 사용 방식이다. 
   14. 표준 오류도 비슷하게 리디렉션하되, `2>`를 사용한다. 
   15. World Bank의 `process_transactions.sh`는 CSV 경로를 위치 인수로 받는다. 2000년 이후 거래는 표준 출력으로, 2000년 이전 거래는 표준 오류로 내보내도록 만들어져 있다. 
   16. 실습에서는 `2020.CSV`를 입력으로 주고, `2>`로 표준 오류를 임시 파일에 저장한다. `/tmp`는 임시 파일을 두는 위치이며 나중에 자동 정리될 수 있으므로 중요한 파일을 보관하지 않는 편이 좋다. 
   17. 생성한 로그 파일을 `cat`으로 열면 1994년, 1995년, 1999년처럼 2000년 이전 거래가 들어 있다. 그 내용을 제출한다. 

### 7.3 표준 입력과 파이프 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/7369.jpg)

1. **표준 입력(stdin)은 프로그램이 실행되는 동안 읽는 데이터 흐름이다.** 
   2. 표준 출력과 표준 오류가 있다면 표준 입력도 있다. `stdin`은 프로그램이 기본적으로 데이터를 읽는 곳이다. 
   3. 표준 입력은 위치 인수와 다르다. 위치 인수와 플래그는 프로그램을 실행할 때 전달되지만, 표준 입력은 프로그램이 실행되는 동안 읽는 스트림이다. 
   4. 대부분의 주요 프로그래밍 언어는 표준 입력을 읽는 방법을 제공한다. Python에서는 `input()`을 사용할 수 있다. 프로그램이 이름을 물으면 입력이 올 때까지 멈춰 기다린다. 
   5. 프로그램은 새 줄 문자를 받을 때까지 표준 입력을 기다린다. 사용자가 Enter를 누르면 입력이 끝났음을 알리는 새 줄 문자가 전달된다. 

6. **World Bank CLI 실습은 `read` 명령으로 표준 입력을 받는다.** 
   7. World Bank CLI 프로그램을 실행하면 환영 문구가 나온 뒤 이름과 이메일을 입력하라는 안내가 표시된다. 
   8. 프로그램은 이름을 입력받을 때까지 대기하고, 사용자가 이름을 입력한 뒤 Enter를 누르면 그 값을 읽는다. 이어 이메일도 같은 방식으로 입력받아 실행을 마친다. 
   9. `cat World Bank.sh`로 코드를 보면 안내 문구를 출력한 뒤 `read name`을 실행한다. 셸의 `read` 명령은 표준 입력에서 새 줄이 들어올 때까지 기다렸다가 값을 변수에 저장한다. 이메일도 같은 방식으로 읽는다. 
   10. 이 실습에서 표준 입력을 읽는 명령은 `read`다. 

11. **파이프는 한 프로그램의 표준 출력을 다음 프로그램의 표준 입력으로 연결한다.** 
   12. 셸의 파이프 연산자는 세로줄 모양의 `|`이며, 왼쪽 프로그램의 표준 출력을 오른쪽 프로그램의 표준 입력으로 보낸다. 
   13. `wc`는 파일 경로뿐 아니라 표준 입력도 읽을 수 있다. `echo "my name is Lane" | wc`처럼 쓰면 문장을 터미널에 표시하는 대신 `wc`에 전달해 계산할 수 있다. 
   14. 강의자는 `wc` 출력의 열이 줄 수, 단어 수, 문자 수를 나타낸다고 정정하며, ASCII 문자에서는 문자 수가 바이트 수와 비슷할 수 있다고 설명한다. 
   15. 조사 실습에서는 Bob이 수상하다는 설정으로, 거래 파일 전체에서 `Bob`이 들어 있는 줄을 찾는다. `grep`을 재귀적으로 실행해 결과를 출력하고, 그 출력을 `wc -l`로 보내 줄 수를 센다. 
   16. 결과는 3,973줄이다. 강의자는 명령을 빠르게 작성해 자신이 맞게 했는지 확신이 크지 않다고 말하지만, 제출 결과는 정답으로 처리된다. 

### 7.4 실행 중인 프로그램 중단과 종료 

강의자는 반응하지 않는 프로그램을 멈추는 방법으로 먼저 `Ctrl+C`를, 그것이 듣지 않을 때는 다른 터미널에서 `ps`로 프로세스를 찾고 `kill`로 종료하는 방법을 보여준다.

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/7627.jpg)

1. **`Ctrl+C`는 프로그램에 중단 신호를 보내는 일반적인 방법이다.** 
   2. 프로그램이 멈춘 것처럼 보이거나, 명령을 잘못 입력했거나, 인터넷 연결을 기다리거나, 너무 많은 데이터를 처리하는 등 여러 이유로 실행을 중단하고 싶을 수 있다. 
   3. `Ctrl+C`는 프로그램에 SIGINT(interrupt) 신호를 보낸다. 프로그램이 이 신호에 반응하도록 만들어져 있으면 실행을 멈춘다. 다만 항상 동작하는 것은 아니다. 
   4. World Bank의 `private/bin/malicious.sh`를 실행하면 화면에 계속 출력이 나온다. `Ctrl+C`를 누르면 프로그램이 종료되고, 스크립트가 신호를 받아 `malicious skulduggery complete` 같은 마지막 문구를 출력하도록 만들어진 것을 확인한다. 

5. **`Ctrl+C`가 통하지 않으면 프로세스 ID를 찾아 `kill`을 실행한다.** 
   6. 어떤 프로그램은 신호에 반응하지 않을 정도로 나쁜 상태에 빠질 수 있다. 이때는 다른 셸 세션이나 터미널 창에서 해당 프로세스를 찾아 강제로 종료할 수 있다. 
   7. `kill`은 첫 번째 위치 인수로 PID(Process ID, 프로세스 ID)를 받는다. 운영체제가 실행 중인 각 프로세스에 부여한 식별 번호다. 
   8. `ps aux`는 다른 사용자의 프로세스를 포함해 실행 중인 프로세스를 보여주고, 각 프로세스에 관한 추가 정보를 표시한다. 종료할 프로그램을 찾을 때 자주 쓰는 조합이다. 
   9. 강의자는 Windows의 Task Manager와 Mac의 Activity Monitor를 GUI에서 프로세스를 확인하거나 종료하는 도구로 언급한다. 
   10. 실습에서는 `malicious.sh`를 강제 실행 모드로 다시 시작한다. 이 모드에서는 `SIGINT`를 무시해 `Ctrl+C`를 눌러도 “Haha, you can't stop me, this is a true virus”라는 문장을 계속 출력한다. 
   11. 두 번째 터미널에서 `ps aux | grep malicious.sh`를 실행해 프로세스를 찾는다. 출력에는 악성 스크립트와 검색용 `grep` 명령이 모두 포함될 수 있다. 
   12. 종료해야 할 대상은 `grep` 프로세스가 아니라 실제 스크립트를 실행한 프로세스다. PID를 확인해 `kill`에 전달한다. 강의자는 PID를 고르는 과정에서 잠시 혼란을 겪지만, 실제 스크립트 프로세스를 찾아 종료한다. 
   13. 원래 터미널에 프롬프트가 돌아오고, `ps`를 다시 확인했을 때 악성 프로세스가 사라지면 종료가 완료된 것이다. `grep` 명령은 검색을 위해 실행한 것이므로 별도로 보일 수 있다. 
   14. 프로그램이 출력한 중단 메시지를 제출하면 실습을 마친다. 

## 8. Unix 철학과 시스템 모니터링 

### 8.1 Unix 철학: 작은 프로그램을 조합한다 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/8079.jpg)

1. **Unix 철학은 한 가지 일을 잘하는 작은 프로그램을 만들어 서로 조합하는 방식이다.** 
   2. Unix 철학은 Mac과 Linux 같은 Unix 계열 운영체제의 개발을 이끌어온 원칙으로, 강의자는 이를 “한 가지 일을 잘하는 프로그램을 작성하라”라고 요약한다. 
   3. 완성형 비디오 게임은 여러 기능, GUI, 상호작용, 소리를 포함하므로 작은 도구를 지향하는 Unix 철학의 대표 예시는 아니다. 그렇다고 게임이 나쁘다는 뜻은 아니다. 
   4. `grep`은 텍스트에서 특정 문자열을 찾는 일을 잘하는 작은 도구이며, 파일 검색뿐 아니라 표준 출력과 파이프를 통해 다른 프로그램과 조합할 수 있다. 
   5. 텍스트, 표준 입력, 표준 출력을 공통 인터페이스로 사용하면 여러 프로그램을 파이프로 연결해 복잡한 자동화를 만들 수 있다. 
   6. 그래서 IT Ops, DevOps, 클라우드 엔지니어는 기존 프로그램을 조합해 많은 일을 자동화할 수 있으며, 모든 작업에 새 소프트웨어를 직접 만들 필요가 없다. 

7. **명령줄은 프로그램의 조합과 확장성 측면에서 강점을 갖는다.** 
   8. 퀴즈에서는 `cat`, `grep`, `ls`, `World of Warcraft.exe` 중 작은 유틸리티의 조합을 지향하는 Unix 철학에 맞지 않는 항목으로 게임 실행 파일을 고른다. 
   9. 확장성과 상호운용성 측면에서 더 강력한 인터페이스를 묻는 문제의 답은 텍스트다. 

### 8.2 `top`으로 자원 사용량 확인하기 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/8219.jpg)

1. **`top`은 실행 중인 프로그램의 CPU와 메모리 사용량을 실시간으로 살펴보는 도구다.** 
   2. `top`은 컴퓨터 자원을 많이 쓰는 프로그램을 보여준다. Windows의 Task Manager와 Mac의 Activity Monitor도 실행 중인 프로그램을 확인할 수 있으며, GUI에서 프로그램을 종료할 수 있다. 
   3. 강의자는 프로세스를 찾아 종료할 때는 `ps`와 `kill`을, 자원 사용량을 확인할 때는 `top`을 주로 쓴다고 설명한다. 
   4. `top`은 `less`나 Nano처럼 프롬프트를 대신하는 대화형 화면을 연다. 현재 녹화 중인 화면에서는 OBS Studio가 CPU 코어 약 2.3개를 사용해 다른 프로그램보다 높은 사용량을 보인다. `q`로 종료한다. 
   5. 화면에는 PID를 포함한 열 이름이 표시되며, PID를 찾아 `kill`에 사용할 수도 있다. 
   6. 앞선 악성 스크립트는 텍스트를 천천히 출력했을 뿐 CPU를 많이 쓰지 않았으므로, 자원 사용량 기준으로 정렬하는 `top`보다 `ps aux`로 찾는 편이 적절했다. 반면 자원을 과도하게 사용하는 프로세스를 찾을 때는 `top`이 유용하다. 
   7. 실습에서는 `top` 화면의 열 이름을 복사해 제출한 뒤 `q`로 나온다. 

## 9. 패키지 관리자와 편집기 

### 9.1 패키지 관리자와 Neovim 설치 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/8426.jpg)

1. **패키지 관리자는 프로그램을 내려받고 설치하며 필요한 의존성을 관리한다.** 
   2. 패키지 관리자는 다른 소프트웨어를 관리하는 소프트웨어다. 컴퓨터에 기본으로 설치된 도구도 있지만, 추가 프로그램은 보통 패키지 관리자를 통해 설치한다. 
   3. Ubuntu에서 기본적으로 많이 쓰는 패키지 관리자는 `apt`이며, `sudo apt-get install` 형태로 사용한다. 
   4. Mac에는 공식 패키지 관리자가 따로 없지만, 널리 사용하는 비공식 도구로 Homebrew가 있다. 설치 명령은 `brew install` 형태다. 

5. **Neovim은 Vim 계열의 확장성이 높은 터미널 편집기이며, 패키지 관리자로 설치할 수 있다.** 
   6. 실습에서는 Neovim을 설치한다. 강의자는 Neovim을 Vim의 새롭고 확장성이 높은 버전, Vim은 VI의 새 버전이라고 소개한다. 
   7. 앞에서 쓴 Nano는 가볍고 거의 모든 시스템에서 사용할 수 있어 알아두면 좋지만, Neovim만큼 기능이 강력하지는 않다. 
   8. Ubuntu WSL 사용자는 Ubuntu용 안내를 따르고, 강의자는 Mac용 안내에 따라 `brew install neovim`을 실행한다. 
   9. 설치가 끝난 뒤 `nvim --version`으로 버전을 확인하며, 강의자의 화면에는 0.10.3이 표시된다. 

10. **Neovim에서는 Normal 모드와 Insert 모드를 구분하고, 저장한 뒤 종료해야 한다.** 
   11. 이 과정은 Neovim 자체를 가르치는 과정은 아니지만, Vim에 들어갔을 때 빠져나오는 법을 보여준다. 
   12. Neovim에서 파일을 열면 기본적으로 **Normal 모드**에 들어가며, 이 상태에서 글자를 누르면 입력하는 대신 커서를 움직이는 기능이 실행될 수 있다. 
   13. `i`를 누르면 **Insert 모드**로 들어가 텍스트를 입력하고 수정할 수 있다. 실습에서는 파일의 비밀번호를 삭제한다. 
   14. `Esc`를 누르면 Normal 모드로 돌아온다. `:w`를 입력하고 Enter를 누르면 저장되며, `:q`를 입력하면 종료된다. Normal 모드에서 단순히 `q`만 누르는 것과 다르다. 
   15. 종료한 뒤 `cat`으로 파일을 확인하면 편집 내용이 반영된 것을 볼 수 있다. 

### 9.2 패키지 관리자 검토 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/8597.jpg)

1. **패키지 관리자는 설치 여부 확인, 다운로드, 설치, 의존성 관리, 경로 설정을 돕는다.** 
   2. `apt`와 Homebrew는 많은 사람이 쓰는 도구지만, 모든 패키지 관리자를 대표하지는 않는다. 특히 Ubuntu와 Mac에서 널리 쓰이는 예다. 
   3. 설치 명령을 실행하면 패키지 관리자는 먼저 해당 프로그램이 이미 설치되어 있는지 확인한다. 
   4. 설치되어 있지 않으면 저장소에서 프로그램을 내려받아 컴퓨터의 파일 시스템에 설치한다. 
   5. 필요한 의존성도 함께 설치한다. 강의자는 의존성 관계를 파악하고 서로 호환되도록 관리하는 일이 패키지 관리자의 어려운 역할이라고 강조한다. 
   6. 가능하다면 설치한 프로그램을 `PATH`에 추가해 어디서든 명령 이름만으로 실행할 수 있게 한다. 
   7. `which neovim`을 실행하면 설치 위치를 확인할 수 있다. 강의자의 시스템에서는 `opt/bin/neovim`이 표시되며, 해당 경로는 `PATH`에 포함되어 있다고 설명한다. 

8. **패키지 관리자는 설치와 의존성 관리를 하지만, 코드의 버그를 디버깅해 고쳐주지는 않는다.** 
   9. 퀴즈에서는 패키지 관리자가 소프트웨어 설치와 의존성 관리, 인터넷에서의 다운로드를 수행한다는 점을 확인한다. 
   10. 반면 프로그램 코드의 오류를 찾아 고치는 일은 패키지 관리자의 역할이 아니다. 

### 9.3 Webby로 웹에서 도구 설치하기와 보안 고려 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/8776.jpg)

1. **Webby는 별도의 로컬 패키지 관리자 없이 웹에서 명령줄 도구의 설치 스크립트를 이용하게 해준다.** 
   2. 강의자는 Webby를 일반적인 패키지 관리자라기보다 “반(反)패키지 관리자”에 가까운 흥미로운 프로젝트로 소개한다. 
   3. `apt`와 Homebrew는 오래되고 기능이 많지만, 새 Mac에는 Homebrew가 기본으로 포함되지 않으므로 먼저 설치해야 한다. 
   4. 강의자의 설명에 따르면 Webby는 로컬 패키지 관리자 없이 웹 서버에서 여러 도구의 공식 설치 스크립트를 제공하며, 하나의 인터페이스에서 설치 지침을 이용하게 한다. 
   5. 실습에서는 Rust로 작성된 것으로 보이는 `ls`의 현대적인 대안 `lsd`를 검색해 설치한다. 강의자는 운영체제를 선택하고 제공된 설치 명령을 터미널에서 실행한다. 
   6. 강의자는 자신의 컴퓨터에 Webby를 별도로 설치하지 않고 `curl` 명령을 직접 실행한다. 설치 결과는 홈 디렉터리 아래 `local/bin/lsd`에 놓였고, `PATH`에도 자동으로 추가된 것으로 보인다고 설명한다. 
   7. `lsd --tree`는 디렉터리 구조를 트리 모양으로 출력하고, `--classic`을 함께 쓰면 색상이 제거된다. 실습에서는 World Bank 거래 디렉터리에서 두 옵션을 조합한 결과를 제출한다. 

8. **웹에서 받은 스크립트를 즉시 실행하면 출처를 신뢰해야 하므로 보안 위험을 이해해야 한다.** 
   9. 강의자는 Webby 유지 관리자 중 한 명인 AJ가 Backend Banter 팟캐스트에 출연해 이 도구를 설명했다고 소개한다. 
   10. 터미널에 붙여 넣는 설치 명령은 원격 서버에서 스크립트를 내려받아 셸 인터프리터에 곧바로 전달해 실행하는 방식이다. 
   11. 서버가 악성 스크립트를 보내면 컴퓨터를 망가뜨리거나 신용카드 번호를 찾는 등 해로운 일을 할 수 있다. 일반적인 조언은 스크립트를 먼저 내려받고, 안전한지 검사한 뒤 실행하는 것이다. 실제 프로그램은 게시자가 서명한 파일인지 확인하는 방법도 중요하다. 
   12. 강의자는 AJ의 주장을 더 자세히 알고 싶으면 팟캐스트를 들어보라고 한 뒤, 핵심 논리를 요약한다. 
   13. 이 설치 방식은 HTTPS를 사용하므로 통신 과정에서 중간자가 스크립트를 바꾸는 공격을 막는 데 도움이 된다. 강의자는 HTTPS로 연결한 서버의 소유자가 보내는 콘텐츠임을 확인할 수 있다는 취지로 설명한다. 
   14. 그러나 HTTPS가 Webby 서버 자체의 안전성을 보장하는 것은 아니다. Webby가 해킹되면 악성 스크립트를 제공할 수 있으므로 Webby를 신뢰해야 한다. 
   15. 불안하다면 스크립트를 먼저 `curl`로 내려받아 읽은 뒤 실행할 수 있다. 결국 설치 출처를 신뢰해야 하며, 강의자는 위험이 전혀 없다고 하지 않고 자신은 위험이 비교적 작다고 본다고 말한다. 
   16. 강의자는 모든 온라인 사용에는 위험이 있다고 덧붙이며, Webby는 사용자의 판단과 책임 아래 사용하라고 한다. 도구 자체는 유용하다고 평가하고, 더 자세한 설명은 팟캐스트를 참고하도록 권한다. 

### 9.4 코드 편집기 선택과 강의 마무리 

![](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/v392lEyM29A/9152.jpg)

1. **편집기는 터미널 편집기와 GUI·터미널을 결합한 편집기 중 작업 환경에 맞게 선택한다.** 
   2. Boot.dev의 Python 입문 과정에서는 브라우저 편집기에서 코드를 작성했지만, 이번 Linux 과정에서는 독립된 터미널을 사용했다. 
   3. 일부 개발자는 Neovim 같은 터미널 편집기로 작업하지만, 강의자는 자신이 그 정도로 능숙한 편집기 사용자는 아니라고 농담한다. 
   4. 강의자는 오랫동안 VS Code를 사용했고, 최근 1년 사이에는 Zed로 옮겼다고 말한다. 
   5. 당시 Zed는 Windows에서 잘 작동하지 않거나 아예 작동하지 않아 WSL 환경에 적합하지 않다고 설명한다. 반면 VS Code는 WSL을 바로 지원한다. 
   6. WSL을 사용하는 초보자에게 강의자는 VS Code를 권한다. Vim을 깊이 배우고 싶다면 Vim이나 Neovim을 살펴볼 수 있고, Emacs도 선택지로 언급되지만 강의자는 별도의 의견을 제시하지 않는다. 
   7. 아직 선호하는 편집기가 없다면 Windows에서는 VS Code, Mac이나 기본 Linux 설치 환경에서는 Zed를 살펴보라고 권한다. 

8. **이 과정은 리눅스 운영체제 전체가 아니라 Unix 계열 명령줄을 시작하는 과정이다.** 
   9. 강의자는 수강자가 과정에서 조금이라도 얻어간 것이 있기를 바라며 강의를 마무리한다. 
   10. 이 과정은 리눅스 운영체제나 커널 전체를 가르치지 않는다. Linux와 흔히 연결되는 Unix 계열 명령줄을 사용하기 시작하도록 돕는 과정이다. 
   11. 많은 개발자가 Mac이나 Windows에서 개발하고 Linux 서버에 배포한다. 그래서 SSH로 서버에 접속해 파일을 살피고, 프로그램을 실행하고, 로그를 확인하는 능력이 중요하다. 
   12. 명령줄은 서버 관리뿐 아니라 로컬 컴퓨터에서 도구를 설치하고 개발 작업을 할 때도 사용한다. 
   13. 강의자는 긴 시간 함께해준 시청자에게 감사 인사를 전한다.
